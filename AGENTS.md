# AGENTS.md

Onboarding for everyone who works on Unhoard: people and AI coding agents alike. Read
this first, then the [docs hub](docs/README.md).

## The project

Unhoard is a free, open-source (GPL-3.0-or-later) Windows app that shows where your disk
space went and helps you get it back safely. It shows the disk as a living cell map,
explains what each big item is and how risky it is to remove, understands OneDrive
placeholders without downloading them, and helps sort a large photo library. A companion
character guides the user with speech bubbles. Stack: Tauri 2, a Rust core and a
React/TypeScript UI. Interface in English and Dutch.

## Ground rules

- **Docs are the source of truth.** If code and docs disagree, fix one of them in the
  same change. A decision and its reason go in [Decisions](docs/24-decisions.md).
- **Everything in the repository is in English:** code, comments, docs, commits and
  issues. User-facing text lives in `src/i18n/` in English and Dutch.
- **Write the current state, not the history.** Docs and comments describe how things
  are. No "previously", "renamed from" or "(was …)": git holds the history.
- **No filler.** Every sentence must help someone build, use or decide.
- **Nothing personal in the repository.** No real file paths, user names, scans or
  photos in code, tests, docs or issues. Test data is generated by the tests.
- **Safety first.** Unhoard never selects, moves or deletes anything without a user click,
  never hydrates an online-only cloud file, and never touches a protected path. These
  invariants (S1–S10) have tests; a change that weakens one is not accepted.
- **AI-assisted contributions are welcome**, disclosed in the pull request and covered by
  tests ([CONTRIBUTING.md](CONTRIBUTING.md)).
- Commits follow Conventional Commits, carry a DCO sign-off (`git commit -s`), and name
  the risk class and the F or S IDs in the body.

## Engineering standards

Each rule is checkable: it maps to a test, a lint, a CI job or a line in the final
report. The safety invariants **S1–S10** and the feature IDs **F1–F11** are defined in
the MVP scope doc.

### Change risk classes

Classify every change before you start, and name the class in the commit body or pull
request (`Risk: high`). The class sets the minimum rigour. When unsure, pick the higher
class.

| Class | Examples in Unhoard | Minimum required |
|---|---|---|
| Low | Layout, styling, animation, copy, filters, view state | Typecheck and lint pass; checked in the running app |
| Medium | Scanning, size totals, metadata, classification, risk tiers, known-locations rules, photo grouping, i18n | TDD (rule 1); edge-case tests (rule 3.6); explicit errors (rule 4) |
| High | Moving to quarantine, restore, "free up space", the elevated helper, any Tauri command that touches the filesystem | Medium, plus failure and attack tests (rules 2–3), an identity check before acting, a recovery path, and a "Security review" paragraph in the report |
| Critical | Permanent deletion (the 30-day purge), bulk operations, anything that touches S1–S10 | High, plus a dry-run test that proves zero writes, an audit-log test, and a separate section in the report with the safety argument, so the maintainer can review it before merging |

### 1. Test-driven development

For every Medium or higher change:
1. Write a test that describes the behaviour, and run it to see it **fail**. That proves
   the test can catch the problem.
2. Write the code until the test **passes**.
3. Refactor while it stays green.

- A bug fix starts with a test that reproduces the bug.
- In a build phase, the test list in the MVP scope doc comes first.
- Test names mention the feature or invariant ID where one applies
  (`s5_manifest_written_before_move`).
- Rust uses `cargo test`, TypeScript uses Vitest.
- Test data is generated in temp folders, never a real disk or real photos.
- Purely visual work is checked by running the app, not by unit tests.

### 2. Security by design

Treat everything from outside the Rust core as untrusted: file names, paths, metadata,
file contents, thumbnails, configuration, data from the webview, and the output of
dependencies or OS tools.

1. **Threat check.** For every Medium or higher change, the report states:
   - the asset at stake
   - the trust boundary crossed
   - the worst case
   - the mitigation

   The threat-model doc in the Trust cluster (assets, trust boundaries, threats and
   mitigations, mapped to these rules and S1–S10) stays current. If it does not exist
   yet, create it.
2. **The webview is untrusted.** Every Tauri command validates its arguments in Rust.
   Destructive commands take scan-index item IDs, never raw path strings from the UI.
   Rust resolves the ID and re-verifies the item (rule 3.5).
3. **Minimal Tauri surface.**
   - Grant each window only the capabilities it needs (`src-tauri/capabilities/`).
   - Use a strict CSP and load no remote content.
   - Never give a plugin a broader `fs` or `shell` scope than it needs.
4. **Least privilege.** The app runs as a normal user. Elevation is only for documented
   opt-in features, in a separate short-lived read-only helper (S7). The UI never runs
   elevated.
5. **Never execute what a scan finds.**
   - Read metadata only.
   - Thumbnails come from the Windows thumbnail API or a memory-safe decoder with size
     and dimension limits.
   - "Open" and "Show in Explorer" happen only on an explicit user click.
6. **Validate at the boundary.** Use allowlists and explicit limits (path length, depth,
   counts, sizes). If something cannot be verified, fail closed.
7. **No leaks.**
   - Keep secrets, file contents and personal paths out of logs, out of errors shown to
     others, out of test output and out of exports.
   - Exported reports replace the profile path with `%USERPROFILE%`, with a test that
     proves the redaction works (S9).
8. **`unsafe` stays in one place.**
   - Only the Windows FFI module may use `unsafe`; every other crate has
     `#![forbid(unsafe_code)]`.
   - Each `unsafe` block carries a `// SAFETY:` comment, enforced by
     `clippy::undocumented_unsafe_blocks`.
9. **Tests are not a security proof.** High and Critical changes get an explicit
   self-review of the diff against this section.

### 3. Safe filesystem operations

This rule applies to anything that moves, renames, deletes, quarantines, restores,
dehydrates, or writes outside the app's own data folder.

1. **Analysis is read-only.** Scanning and classification never change files,
   timestamps or attributes.
2. **Preview first.** Every bulk or destructive operation has a dry run that returns
   exactly what would happen: the items, total size, destination, and skipped items with
   a reason. A test proves that a dry run writes nothing (the temp tree is identical
   before and after).
3. **Permanent deletion happens only in the 30-day purge.** It works only inside the
   quarantine root, and only on items whose manifest entry still matches (S1, S6). Users
   delete earlier themselves in Explorer; the app has no delete-now button.
4. **Write-ahead manifest (S5).**
   - Before a move starts, write and flush its manifest entry: original path, file ID,
     size, timestamps, operation ID and time.
   - On startup, reconcile any operation that did not finish.
5. **Verify identity right before acting.**
   - Open the item with `FILE_FLAG_OPEN_REPARSE_POINT` (plus
     `FILE_FLAG_BACKUP_SEMANTICS` for folders).
   - Compare the volume serial and 128-bit file ID (`FILE_ID_INFO`), the size and the
     last-write time with the scan.
   - Then act through that same handle (rename with `SetFileInformationByHandle`).
   - On a mismatch, skip the item and report it. Never act on a path string from an
     earlier scan alone.
6. **Odd cases are explicit cases, each with a test:**
   - junctions, symlinks and other reparse points, which are never followed out of scope
   - hard links, which are counted once
   - locked files and access denied
   - long paths (`\\?\`)
   - Unicode names and names with trailing dots or spaces
   - files that vanish mid-operation
   - a full disk
7. **Cloud placeholders.** Check the attributes before any open.
   - Never open a placeholder for its data (S2).
   - Never move cloud files into the quarantine (S3).
   - "Free up space" changes only the pin state.
8. **Cross-volume moves** copy, verify (size plus hash), then delete the source. The
   source is never deleted before the copy is verified.
9. **Restore never overwrites.** If the original path exists, restore next to it as
   `name (restored).ext` and say so. Recreate missing parent folders.
10. **Partial failure is reported per item:** what succeeded, what failed and why.
    Recovery information is never dropped.
11. **Audit log.** Every move, restore and purge appends to a local audit log: the
    operation, item IDs and result, never file contents.
12. **Tests use generated trees** in temp folders (`tempfile`), never a real profile or
    real photos.

### 4. Explicit error handling

- **Rust:**
  - Library crates use typed errors (`thiserror`); `anyhow` is only for the binary edge
    (CLI, Tauri entry).
  - No `unwrap`, `expect` or `panic!` outside tests: set `clippy::unwrap_used`,
    `clippy::expect_used` and `clippy::panic` to deny.
  - Add context when propagating an error.
- **TypeScript:**
  - `strict` mode and no `any`.
  - No `@ts-ignore` without a written reason.
  - No empty `catch` and no floating promises (lint rules).
  - Every IPC call handles its error case in the UI.
- **Scans survive bad folders.** An error is counted, kept with its path and shown
  ("unreadable"). It is never swallowed and never stops the scan.
- **No misleading defaults.** An unknown size is "unknown", never 0. User messages say
  what to do next and do not expose internals.

### 5. Architecture and simplicity

- **Layers point inwards, with no cycles:**

  | Layer | Contents |
  |---|---|
  | `core` | Model, totals, classification and rules; no real I/O |
  | `platform` | Windows filesystem, cloud attributes, thumbnails, elevation, all behind traits that tests can replace |
  | `app` | Tauri commands and state |
  | `ui` | React; it renders and never decides safety |
  | `cli` | The command-line tool |

- **No speculative building.** Reuse an existing abstraction before adding one. Add no
  dependency, framework, abstraction or setting without a concrete requirement in the
  docs.
- **Hard-to-reverse choices get a proposal first** in the decisions doc: options,
  trade-offs, risks. In a build phase, decide yourself when the docs already settle the
  question, record it, and keep going. A one-shot build does not stall on details.
- **Simplest first.** Choose the simplest design that meets the acceptance criteria.
  Optimise only after measuring.

### 6. Readability

- Every file starts with a header comment that says what it is for.
- Every function and type gets a doc comment (`///` in Rust, TSDoc in TypeScript).
- Add "why" comments where the reason is not obvious. No line-by-line narration.
- Descriptive names and small, cohesive functions. No dead or commented-out code. No
  duplicated business logic.

### 7. Performance and resources

- Scans stream metadata. Never read whole files when metadata is enough. Hashing reads
  in chunks, and only for files that need it.
- Use bounded concurrency (a fixed worker pool), cancellation for every long operation,
  and progress events at a fixed rate. The UI stays responsive during a scan.
- The architecture doc states the memory budget per scanned entry. Check it with a
  generated tree of at least 1 million entries, and record the numbers in the report.
- **Speed budgets are hard limits.** The performance doc sets them (P1–P14), for example
  a screen switch painted within 100 ms. A change that touches the UI, the core's hot
  paths or IPC runs `cargo bench -p unhoard-core`, `npm run perf` and
  `npm run perf:check` before and after, and the report lists the numbers. A budget
  breach or a regression over the threshold is not done.

### 8. Dependencies and supply chain

- **Before adding a dependency,** check:
  - that it is really needed
  - its maintenance (recent releases, open issues) and adoption
  - its `unsafe` use and transitive weight
  - its license

  Every dependency's reason goes in the decisions doc.
- **Licenses are compatible with GPL-3.0.** `cargo deny check` enforces this, along with
  advisories, bans and sources, through `deny.toml`. It covers the RustSec advisories, so
  a separate `cargo audit` is not needed.
- **Lockfiles.** Commit `Cargo.lock` and `package-lock.json`. CI installs with `npm ci`
  and runs `npm audit --audit-level=high`.
- **GitHub Actions** are pinned to a full commit SHA, with the version in a comment.
  Dependabot keeps them current.

### 9. Documentation and traceability

- When behaviour, architecture, configuration or the UI changes, update the matching doc
  in the same change.
- Feature IDs (F1–F11) and invariant IDs (S1–S10) appear in test names and commit bodies
  where relevant, so every requirement traces to a test.
- **Docs layout:** a flat `docs/` with no subfolders and the hub `docs/README.md`.
  - Each file is a two-digit number plus a kebab-case name (`05-mvp-scope.md`), so the
    folder lists in order.
  - The first digit is the cluster: `0x` Product, `1x` Features, `2x` Engineering,
    `3x` Trust.
  - A new doc takes the next free number in its cluster. Existing docs keep their
    number.
- **Every doc** starts with a breadcrumb, and ends with "Related in this cluster" plus a
  link to the hub.
- **Adding or renaming a doc** means updating the hub, `llms.txt` and the root README
  links in the same change.
- **No version numbers** in docs or the roadmap. The roadmap uses Now / Next / Later.

### 10. Definition of done

A change is done only when all of this is true. The final report says which checks ran
and their result.

1. Tests were written first, as the risk class requires, and they pass.
2. These checks pass:
   ```
   cargo fmt --all --check
   cargo clippy --workspace --all-targets --all-features -- -D warnings
   cargo test --workspace
   cargo deny check
   npm run typecheck
   npm run lint
   npm test
   npm run build
   ```
   If a check does not exist yet, say so. Never report it as passed.
3. The diff is self-reviewed: no unintended changes, debug code, commented-out code,
   duplicated logic, history notes, secrets or personal data. `git status` shows nothing
   from `private/` and no `CLAUDE.md`.
4. The docs are updated (rule 9).
5. The report lists what changed, the risk class, which checks passed, and the known
   limitations.
